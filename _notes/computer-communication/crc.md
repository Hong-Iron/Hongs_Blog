<div class="callout-title callout-title--default" markdown="span">요약</div>

보내는 쪽과 받는 쪽이 비트 모양 하나(젯수)를 미리 정해 둔다. 보내는 쪽은 메시지 뒤에 몇 비트를 붙여 전체가 젯수로 나누어떨어지게 만들고, 받는 쪽은 받은 프레임을 같은 젯수로 나눠 나머지가 0인지 본다. 이 "나누기"는 보통의 나눗셈이 아니라 자리올림 없는 XOR 연산이라 하드웨어로 거의 공짜에 가깝게 계산된다. 젯수를 잘 고르면 32비트로도 오류를 거의 다 잡는다. 다만 오류 모양이 젯수의 배수와 같으면 놓친다.

</div>


## 예시로 보기

나눗셈으로 확인하는 생각을 10진수로 먼저 보자(실제 CRC는 10진 연산을 쓰지 않는다). 두 사람이 젯수 11을 약속했다. 데이터 331을 보낼 때, 331 뒤에 한 자리 $$x$$를 붙여 $$331x$$가 11로 나누어떨어지게 한다. $$3311 = 11 \times 301$$이라 1을 붙여 3311을 보낸다[^1].

| 받은 수 | 11로 나눈 나머지 | 판단 |
|---|---|---|
| 3311 | 0 | 오류 없다고 본다 |
| 3310 | 0 아님 | 오류 검출 |
| 2311 | 0 아님 | 오류 검출 |
| 2211 | 0 | 오류를 놓침 |

붙이는 자리 수는 (젯수의 자리 수 − 1)이다. 젯수를 10으로 정하면 마지막 자리만 보게 되어 앞자리 오류는 하나도 못 잡는다. 검출율은 젯수에 달려 있다[^1].

## 정의

**입력:** 메시지 $$M$$, 약속한 $$(k + 1)$$비트 젯수 $$C$$. **출력:** $$M$$ 뒤에 붙일 $$k$$비트 $$F$$(EDC).

보내는 쪽은 $$(M \Vert  F) \bmod C = 0$$이 되도록 $$F$$를 만든다. 곧 $$F$$에 나머지를 넣어 프레임 전체가 $$C$$로 나누어떨어지게 하고 $$M \Vert  F$$를 보낸다. 받는 쪽은 받은 프레임 전체를 $$C$$로 나눠 나누어떨어지지 않으면 오류, 나누어떨어지면 오류가 없는 것으로 본다[^2].

### 다항식으로 보기

$$n$$비트 메시지를 $$n - 1$$차 다항식으로 쓴다. 비트가 1인 자리의 $$x$$ 거듭제곱을 더한다[^3].

- $$M = 10011010 \;\to\; M(x) = x^7 + x^4 + x^3 + x$$
- $$C = 1101 \;\to\; C(x) = x^3 + x^2 + 1$$ ($$k = 3$$)

계수는 0과 1뿐이고 더하기와 빼기가 모두 XOR이다($$1 + 1 = 0$$, 자리올림 없음). 그래서 나눗셈도 "앞자리가 1이면 젯수를 XOR"의 되풀이다. 필기의 말대로 나누기가 아니라 XOR 연산이라는 것을 기억해야 한다[^4].

### 보내는 쪽 절차

1. $$M(x)$$에 $$x^k$$를 곱한다. 뒤에 0을 $$k$$개 붙여 $$F$$가 들어갈 자리를 만든다: $$10011010\,000$$.
2. $$C(x)$$로 나눈다.
3. 나머지를 더한(XOR한) $$P(x)$$를 보낸다. $$P(x)$$는 $$C(x)$$로 나누어떨어진다[^3].

```
              11111001          ← 몫
      ┌──────────────
 1101 │ 10011010000
        1101
         1001
         1101
          1000
          1101
           1011
           1101
            1100
            1101
              1000
              1101
               101              ← 나머지 F
```

보내는 프레임은 $$10011010\,101$$이다[^3]. 슬라이드는 "$$10011010000 - 101 = 10011010101$$"로 적는다. 여기서 −는 XOR이다. 보통의 2진 뺄셈이었다면 $$10011001011$$이 된다[^s1].

### 스스로 설명해 보기

1. "0을 $$k$$개 붙여 나눈 나머지를 더하면 나누어떨어진다"
   <details class="inline-fold" markdown="1"><summary markdown="span">근거</summary>
   $$x^kM(x) = Q(x)C(x) + R(x)$$이다. 양변에 $$R(x)$$를 더하면 XOR 덧셈에서 $$R + R = 0$$이라 $$x^kM(x) + R(x) = Q(x)C(x)$$다. 보내는 $$P(x)$$가 바로 $$x^kM(x) + R(x)$$다.
   </details>
2. "받는 쪽 나머지는 오류 모양에만 달려 있다"
   <details class="inline-fold" markdown="1"><summary markdown="span">근거</summary>
   받은 프레임은 $$P(x) + E(x)$$이고 $$P$$는 $$C$$로 나누어떨어지므로 나머지는 $$E(x) \bmod C(x)$$다. $$E$$가 $$C$$의 배수일 때만 놓친다. 검증 코드에서 $$E = 1101000$$($$C$$를 세 칸 옮긴 것)을 놓쳤다.
   </details>
3. "1비트 오류는 늘 잡는다"
   <details class="inline-fold" markdown="1"><summary markdown="span">근거</summary>
   1비트 오류는 $$E(x) = x^i$$다. $$C(x)$$에 항이 둘 이상이면 어떤 $$x^i$$도 $$C(x)$$의 배수가 될 수 없어 나머지가 0이 아니다.
   </details>
- 이 방법의 핵심 아이디어는?
  <details class="inline-fold" markdown="1"><summary markdown="span">답</summary>
  정해 둔 젯수로 나누어떨어지도록 꼬리를 붙이면, 받는 쪽은 나머지 하나로 검사한다. 그 나머지는 오류 모양에만 달려 있어서 젯수를 잘 고르면 흔한 오류 모양을 모두 잡는다.
  </details>
- 같은 논리를 쓰는 다른 상황은?
  <details class="inline-fold" markdown="1"><summary markdown="span">답</summary>
  ISBN 같은 번호의 검증 숫자(나머지로 확인하는 10진판), 파일 압축(ZIP·PNG의 CRC-32), 저장 장치의 오류 검출.
  </details>

### 성능과 표준 젯수

검출율은 젯수 $$C$$의 선택이 좌우한다. 수학적 분석으로 잘 고르면 32비트 코드로 1500바이트가 넘는 데이터에서도 99.99…%를 잡는다[^5]. 계산이 전송보다 느리면 CRC 계산이 전송 시간을 정하므로, 가능하면 네트워크 어댑터 안의 하드웨어로 한다. 송수신 양쪽이 같은 $$C$$를 써야 하므로 표준화된 젯수를 쓴다[^5][^6].

| CRC | $$C(x)$$ |
|---|---|
| CRC-8 | $$x^8 + x^2 + x + 1$$ |
| CRC-10 | $$x^{10} + x^9 + x^5 + x^4 + x + 1$$ |
| CRC-12 | $$x^{12} + x^{11} + x^3 + x^2 + 1$$ |
| CRC-16 | $$x^{16} + x^{15} + x^2 + 1$$ |
| CRC-CCITT | $$x^{16} + x^{12} + x^5 + 1$$ |
| CRC-32 | $$x^{32} + x^{26} + x^{23} + x^{22} + x^{16} + x^{12} + x^{11} + x^{10} + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1$$ |

### 하드웨어 구현

1비트 래치와 XOR 게이트를 $$C$$에 따라 잇는다. 길이가 ($$C$$의 비트 수 − 1)인 시프트 레지스터의 칸 사이, $$C$$의 계수가 1인 자리 앞에 XOR을 둔다. $$C = 1101$$이면 $$x^0$$ 칸 앞과 $$x^2$$ 칸 앞에 XOR이 놓이고, 맨 끝 칸의 값이 되먹임된다. 모든 비트가 지나간 뒤 래치에 남은 값이 CRC다. 메시지를 보내면서 동시에 계산하고, 끝나면 CRC를 뒤에 붙여 보낸다[^7]. 그래서 CRC는 늘 프레임 끝에 온다. 계산 비용이 거의 없다[^4][^s1].

$$C = 1101$$일 때의 회로는 다음과 같다. `in`은 들어오는 비트, `x0`~`x2`는 1비트 래치 칸이다. 박자마다 값이 오른쪽 칸으로 한 칸씩 옮겨 간다.

```
         ┌───────────────────────────────┬────────────────┐
         │                               │                │
         ↓                               ↓                │
in ──→ (XOR) ──→ [ x0 ] ──→ [ x1 ] ──→ (XOR) ──→ [ x2 ] ──┘
```

`x2` 칸에서 나온 값이 위의 선을 타고 두 갈래로 되돌아가, `x0` 앞과 `x2` 앞의 XOR에 들어간다. 두 XOR의 자리는 $$C(x) = x^3 + x^2 + 1$$에서 계수가 1인 $$x^0$$, $$x^2$$ 자리다. 계수가 0인 $$x^1$$ 앞에는 XOR이 없다[^s2].

## 예제

**$$M = 1101$$, $$C = 1011$$.**

- 목표 1, 0 붙이기: $$k = 3$$이라 $$1101\,000$$.
- 목표 2, XOR 나눗셈: $$1101 \oplus 1011 = 0110$$ → 내려 $$1100 \oplus 1011 = 0111$$ → 내려 $$1110 \oplus 1011 = 0101$$ → 내려 $$1010 \oplus 1011 = 0001$$.
- 목표 3, 나머지 붙이기: $$F = 001$$, 보내는 프레임 $$1101\,001$$.

## 활용

- 이더넷과 무선랜 어댑터가 CRC-32를 쓴다. 검출율이 매우 높고 하드웨어로 만들 수 있어 거의 모든 링크 전송에서 쓴다[^6].
- 복잡도: 메시지 $$n$$비트에 대해 하드웨어는 비트마다 한 박자, $$O(n)$$. 소프트웨어는 표를 써서 바이트마다 처리한다.
- 시험 대비: 슬라이드 p.57 "CRC에 대해 간단히 설명하시오"의 답 틀은 "부가되는 오류 검출 코드 → 송신자가 계산해 붙이고 수신자가 확인 → 프레임 전체가 젯수로 나누어떨어지게 만들고 나머지가 0이 아니면 오류 → 검출율이 매우 높고 하드웨어 구현이 가능해 거의 모든 링크에서 사용(CRC-32)"이다[^6].
- 흔한 실수: 나눗셈에서 자리올림·빌림을 하는 것. CRC의 빼기는 XOR이다. 또 0을 $$k$$개가 아니라 $$k + 1$$개 붙이는 것.

## 자주 하는 오해

<div class="callout callout-misconception" markdown="1">
<div class="callout-title" markdown="span">"CRC는 메시지를 젯수로 나눈 보통의 나머지다"</div>

틀렸다. 이름에 "나누기"가 있고 슬라이드도 10진 비유로 설명해서 그럴듯하다. 실제로는 계수가 0과 1인 다항식의 나눗셈이라 더하기와 빼기가 모두 XOR이고 자리올림이 없다. 슬라이드의 마지막 줄 "$$10011010000 - 101$$"도 보통의 뺄셈이면 $$10011001011$$이지만 XOR이라 $$10011010101$$이다. 손으로 계산할 때 빌림을 하면 답이 틀린다.

</div>


## 확인 문제

<details markdown="1"><summary markdown="span"><b>C1</b> CRC에서 보내는 쪽과 받는 쪽이 하는 일을 쓰라.</summary>


**답:** 보내는 쪽은 메시지 뒤에 0을 $$k$$개 붙여 젯수 $$C$$($$k + 1$$비트)로 XOR 나눗셈을 하고, 나머지 $$k$$비트를 붙여 보낸다. 받는 쪽은 받은 프레임 전체를 $$C$$로 나눠 나머지가 0이 아니면 오류로, 0이면 오류가 없는 것으로 본다.

</details>

<details markdown="1"><summary markdown="span"><b>C2</b> $$M = 1101$$, $$C = 1011$$로 보낼 프레임을 구하라.</summary>


**답:** $$1101000$$을 $$1011$$로 XOR 나눗셈하면 나머지 $$001$$. 보내는 프레임은 $$1101001$$.

</details>

<details markdown="1"><summary markdown="span"><b>C3</b> 받는 쪽 나머지가 오류 모양 $$E(x)$$에만 달려 있는 이유는?</summary>


**답:** 받은 프레임은 $$P(x) + E(x)$$이고 $$P(x)$$는 $$C(x)$$로 나누어떨어진다. 그래서 나머지는 $$E(x) \bmod C(x)$$다. 데이터가 무엇이든 같은 오류 모양이면 같은 나머지가 나온다.

</details>

<details markdown="1"><summary markdown="span"><b>C4</b> 비트열 $$10011010$$과 $$1101$$을 다항식으로 쓰라.</summary>


**답:** $$x^7 + x^4 + x^3 + x$$와 $$x^3 + x^2 + 1$$. 왼쪽 끝 비트가 가장 높은 차수이고, 1인 자리의 거듭제곱만 더한다.

</details>

<details markdown="1"><summary markdown="span"><b>C5</b> CRC 하드웨어(시프트 레지스터와 XOR)가 하는 일을 한 문장으로 쓰라.</summary>


**답:** 메시지 비트를 한 박자에 하나씩 밀어 넣으며, 맨 앞 비트가 1일 때마다 젯수를 XOR하는 나눗셈을 레지스터 안에서 그대로 해, 마지막에 레지스터에 나머지(CRC)를 남긴다.

</details>
